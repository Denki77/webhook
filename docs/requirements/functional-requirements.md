# Functional Requirements

## Назначение документа

Этот документ описывает функциональные требования и ожидаемое поведение Webhook Delivery Service.

Функциональные требования определяют:

* какие операции должна выполнять система;
* какие данные она должна принимать и предоставлять;
* какие состояния должны поддерживаться;
* как сервис должен реагировать на события и ошибки;
* какие действия доступны клиентам и уполномоченным сотрудникам.

Документ не определяет:

* конкретную архитектуру;
* язык программирования;
* способ хранения данных;
* способ передачи данных;
* способ масштабирования;
* внутреннее устройство обработчиков.

Числовые параметры, политики и критерии, которые ещё не утверждены, обозначаются как `TBD`.

---

## 1. Состояния и жизненный цикл доставки

### FR-001. Состояния доставки события

Сервис должен поддерживать состояния, позволяющие отличить как минимум:

* событие, принятое для доставки;
* событие, ожидающее начала доставки;
* событие, находящееся в обработке;
* успешно доставленное событие;
* событие, доставка которого окончательно прекращена;
* событие, доставка которого прекращена из-за состояния подписки.

Конкретный перечень состояний и допустимые переходы между ними должны быть определены отдельно в модели жизненного цикла
доставки.

### FR-002. Информация о состоянии доставки

По запросу о состоянии доставки сервис должен предоставлять как минимум:

* идентификатор события;
* родительский идентификатор события, если он существует;
* тип события;
* идентификатор клиента;
* идентификатор подписки;
* время возникновения события, если оно передано в сервис;
* время принятия события сервисом;
* текущее состояние доставки;
* время успешной доставки, если она состоялась;
* количество выполненных попыток;
* причину текущей или итоговой ошибки.

### FR-003. История изменения состояния доставки

Сервис должен сохранять историю значимых изменений состояния доставки.

Для каждого изменения должны быть доступны:

* предыдущее состояние;
* новое состояние;
* время изменения;
* причина изменения.

### FR-004. Итоговое состояние принятого события

Каждое событие, за которое сервис принял ответственность, должно либо:

* перейти в состояние успешной доставки;
* оставаться в явно определённом промежуточном состоянии;
* перейти в явно определённое итоговое состояние прекращённой доставки.

Принятое событие не должно исчезать без зафиксированного состояния.

## 2. Каталог типов событий

### FR-005. Каталог событий

По решению бизнеса перечень поддерживаемых типов событий определяется до начала архитектурного проектирования.

Конкретный перечень типов событий находится за пределами публичной версии документации.

Сервис должен предоставлять зарегистрированным клиентам машиночитаемый список поддерживаемых типов событий и их версий.

При изменении списка событий будет запрашиваться отдельная разработка.

Конкретная политика должна фиксироваться отдельным бизнес-решением.

---

## 3. Управление клиентами

### FR-006. Подписка (регистрация) клиента

Клиент должен иметь возможность подписаться, зарегистрироваться в сервисе.

Для регистрации в сервисе клиент предоставляет как минимум:

* endpoint, на который он планирует получать вебхук;
* дополнительные настройки, необходимые для регистрации клиента.

При регистрации клиента сервис должен проверить доступность endpoint.

### FR-007. Проверка endpoint при регистрации клиента

Перед регистрацией клиента сервис должен проверить доступность endpoint.

Если проверка завершилась неуспешно:

* регистрация отклоняется;
* клиент должен получить причину отказа;
* если клиент был зарегистрирован ранее — его статус должен быть обновлен на не активный.

### FR-008. Удаление клиента

Клиент должен иметь возможность удалить свою регистрацию.

После удаления:

* новые события не должны назначаться клиенту;
* новые подписки не могут быть созданы;
* существующие подписки удаляются.

Доставка событий, уже переданных исполнителям до момента удаления клиента, может быть завершена.

Для удаления себя в сервисе клиент предоставляет только свои идентификационные данные.

### FR-009. Просмотр клиента

Клиент должен иметь возможность просмотреть свою регистрацию в сервисе.

Сервис должен отдавать клиенту информацию как минимум:

* статус клиента;
* endpoint;
* дополнительные настройки клиента.

### FR-010. Изменение данных клиента

Клиент должен иметь возможность изменить свои данные регистрации в сервисе.

Для этого клиент присылает обновленные свои данные, в объёме как для регистрации.

## 4. Управление подписками

### FR-011. Создание подписки

Клиент должен иметь возможность создать подписку на доступный ему тип события.

Для создания подписки клиент должен предоставить как минимум:

* тип события;
* дополнительные настройки, необходимые для подписки на этот тип события.

### FR-012. Создание или обновление подписки

Перед созданием подписки сервис должен проверить:

* существует ли регистрация клиента;
* находится ли клиент в состоянии `active`.

Если подписка на указанный тип события отсутствует — должна быть создана новая подписка.

Если подписка уже существует — сервис должен обновить её параметры в соответствии с полученными данными.

Создание дублирующих подписок на один и тот же тип события не допускается.

### FR-013. Просмотр подписок

Клиент должен иметь возможность получить список собственных подписок.

Для каждой подписки должны быть доступны как минимум:

* идентификатор;
* тип события;
* состояние;
* дата создания;
* дата последнего изменения;
* причина отключения, если подписка отключена.

### FR-014. Просмотр подписки

Клиент должен иметь возможность получить подробную информацию о конкретной собственной подписке.

Клиент не должен иметь возможность получить информацию о подписке другого клиента.

### FR-015. Добровольная приостановка подписки

Клиент должен иметь возможность самостоятельно перевести активную подписку в состояние `paused`.

После перехода подписки в `paused` новые события не должны назначаться для доставки по этой подписке.

Политика в отношении уже ожидающих доставок должна быть определена отдельно.

### FR-016. Добровольное возобновление подписки

Клиент должен иметь возможность возобновить подписку из состояния `paused`.

### FR-017. Удаление или прекращение подписки клиентом

Клиент должен иметь возможность окончательно отказаться от подписки.

После прекращения подписки:

* новые события не должны назначаться для доставки;
* ожидающие доставки должны быть обработаны по утверждённому правилу;
* история подписки должна сохраняться;
* подписка не должна автоматически восстанавливаться.

---

## 5. Автоматическая деактивация проблемного клиента

### FR-018. Выявление проблемной клиента

Сервис должен учитывать результаты попыток доставки для определения продолжительной или систематической недоступности
получателя.

Критерии признания подписки проблемной должны быть определены отдельно.

### FR-019. Автоматическая деактивация клиента

При выполнении критериев продолжительной или систематической недоступности endpoint сервис должен автоматически
перевести клиента в состояние `disabled`.

После деактивации новые доставки не должны создаваться ни по одной подписке клиента.

Операция не должна требовать участия сотрудника.

### FR-020. Фиксация причины автоматической деактивации

При автоматическом переводе клиента в состояние `disabled` сервис должен зафиксировать:

* время деактивации;
* причину;
* критерий, вызвавший деактивацию;
* количество предшествовавших ошибок;
* время начала периода проблем;
* последнюю зарегистрированную ошибку.

### FR-021. Прекращение ожидающих доставок

При переводе клиента в состояние `disabled` все ожидающие доставки события, относящиеся к этому клиенту, должны быть
прекращены.

Для каждой прекращённой доставки должна быть зафиксирована причина `client_disabled`.

### FR-022. Изоляция отключаемого клиента

При прекращении ожидающих доставок сервис должен затронуть только доставки отключаемого клиента.

### FR-023. Обработка доставок во время отключения клиента

При переводе клиента в состояние `disabled` сервис должен прекратить создание новых попыток доставки.

Доставка, которая уже была передана исполнителю до момента отключения клиента, может завершить текущую попытку.

Все последующие попытки доставки должны быть прекращены.

### FR-024. Самостоятельное восстановление клиента из состояния `disabled`

Клиент должен иметь возможность самостоятельно запросить восстановление
из состояния `disabled`.

Для восстановления клиент должен повторно пройти проверку endpoint
в соответствии с FR-006 и FR-007.

После успешной проверки клиент переводится в состояние `active`.

Автоматическое отключение клиента не изменяет состояния его подписок.

После восстановления клиента доставка новых событий автоматически
возобновляется по подпискам, находящимся в состоянии `active`.

Подписки в состояниях `paused` или `terminated` не активируются
автоматически.

Создание новой регистрации клиента или новых подписок не требуется.

### FR-025. Возобновление без ранее прекращённых доставок

После успешного восстановления клиента новые доставки должны создаваться
только для событий, принятых после перехода клиента в состояние `active`.

Ранее прекращённые доставки не должны:

* восстанавливаться;
* возвращаться в обработку;
* отправляться повторно;
* считаться ожидающими доставки.

## 6. Приём событий

### FR-026. Приём события

Сервис должен принимать от внутренних источников события, предназначенные для внешней доставки.

Принимаемое событие должно содержать как минимум:

* уникальный идентификатор;
* родительский идентификатор события, если он существует;
* тип события;
* версию контракта;
* время возникновения;
* данные события, если применимо;
* идентификатор источника, если применимо;
* корреляционные идентификаторы, если они предусмотрены.

### FR-027. Валидация события

Перед принятием ответственности сервис должен проверить:

* наличие обязательных полей;
* корректность типа события;
* поддерживаемость версии;
* корректность структуры данных;
* допустимость размера.

### FR-028. Отказ в принятии события

Если событие не прошло обязательную проверку, сервис должен:

* не принимать ответственность за дальнейшую доставку;
* вернуть однозначный результат отказа;
* указать допустимую для раскрытия причину;
* зафиксировать факт отказа.

### FR-029. Подтверждение принятия события

Если событие прошло обязательные проверки и сервис принял ответственность за дальнейшую обработку, источник должен
получить подтверждение принятия.

Подтверждение должно содержать как минимум:

* идентификатор события;
* результат принятия;
* время принятия;
* идентификатор запроса или операции, если применимо.

### FR-030. Повторное получение события

Сервис не накладывает ограничений на повторное получение событий с одинаковыми внешними идентификаторами.

Каждое принятое событие рассматривается как самостоятельный экземпляр обработки.

После успешного принятия сервис присваивает событию собственный внутренний идентификатор, который используется во всех
дальнейших операциях обработки, доставки и отслеживания состояния.

### FR-031. Родительские и связанные события

Если событие связано с другим событием, сервис должен сохранять переданный родительский или корреляционный
идентификатор, для дальнейшей передачи.

Наличие связи не должно автоматически означать обязательный порядок доставки, если такой порядок не определён отдельно.

### FR-032. Определение получателей события

Для каждого принятого события сервис должен определить полный набор клиентов, имеющих активные подписки на
соответствующий тип события.

Каждый найденный клиент должен рассматриваться независимо от остальных.

Ошибка обработки одного клиента не должна влиять на определение остальных получателей.

Способ сопоставления клиентов и подписок:

* тип события совпадает;
* событие доступно клиенту;
* версия контракта поддерживается;
* подписка находится в состоянии `active`;
* дополнительные условия подписки выполнены.

### FR-033. Отсутствие маршрутов доставки

Если после определения маршрутов обработки для события не найдено ни одного получателя, сервис должен прекратить
дальнейшую обработку этого события.

Хранение события без возможности дальнейшей обработки не производится.

### FR-034. Мультимачт событий

Для одного события может быть несколько получателей.

Одному событию могут подходить несколько подписок.

---

## 7. Формирование доставок

### FR-035. Создание доставки для подписки

Для каждой применимой активной подписки сервис должен создать отдельную доставку события.

Перед отправкой сервис должен сформировать сообщение в соответствии с версией интеграционного контракта подписки.

Одна доставка должна быть связана как минимум с:

* событием;
* клиентом;
* подпиской;
* endpoint;
* версией контракта;
* текущим состоянием;
* историей попыток.

### FR-036. Независимость доставок

Результат доставки одному получателю не должен автоматически определять результат доставки того же события другим
получателям.

Для каждой подписки должен существовать собственный результат доставки.

### FR-037. Формирование внешнего сообщения

Перед отправкой сервис должен сформировать сообщение в соответствии с версией интеграционного контракта подписки.

Каждое сообщение должно содержать как минимум:

* идентификатор события;
* тип события;
* время возникновения;
* данные события;
* версию.

### FR-038. Фиксация версии контракта

Для каждой доставки сервис должен зафиксировать версию интеграционного контракта клиента, использованную при
формировании сообщения.

Последующее изменение версии контракта клиента не должно изменять уже созданные доставки.

---

## 8. Выполнение доставки

### FR-039. Выполнение попытки доставки

Сервис должен отправить сформированное сообщение на endpoint клиента.

Для каждой попытки должны быть зафиксированы:

* порядковый номер попытки;
* время начала;
* время завершения;
* результат;
* категория ответа;
* допустимые для хранения сведения об ошибке.

### FR-040. Определение успешной доставки

Доставка должна считаться успешной, если получатель вернул подтверждение, которое согласно интеграционному контракту
означает принятие уведомления.

Для HTTP-интеграции по умолчанию успешным считается ответ с кодом `2xx`, если контрактом не определено иное.

### FR-041. Фиксация успешной доставки

После получения успешного подтверждения сервис должен:

* перевести доставку в итоговое успешное состояние;
* сохранить время доставки;
* сохранить сведения о подтверждении;
* прекратить дальнейшие попытки.

### FR-042. Классификация ошибки доставки по типу временности

Неуспешный результат попытки должен быть классифицирован как минимум как:

* временная ошибка;
* постоянная ошибка;

### FR-043. Классификация ошибки доставки по типу ошибки получателя

Неуспешный результат попытки должен быть классифицирован как минимум как:

* недоступность endpoint;
* превышение времени ожидания;
* некорректный ответ получателя;
* внутренняя ошибка сервиса.

Конкретная классификация должна быть определена отдельно.

### FR-044. Обработка временной ошибки

При временной ошибке сервис должен:

* зафиксировать результат попытки;
* сохранить причину;
* назначить следующую попытку в соответствии с политикой повторов;
* оставить доставку в промежуточном состоянии.

### FR-045. Обработка постоянной ошибки

При постоянной ошибке сервис должен:

* зафиксировать результат;
* прекратить дальнейшие попытки этой доставки;
* перевести доставку в итоговое неуспешное состояние;
* сохранить причину прекращения.

### FR-046. Превышение допустимого числа попыток

Если количество попыток достигло установленного предела, сервис должен:

* перевести состояние клиента в `disabled`;
* прекратить новые попытки;
* зафиксировать итоговое состояние;
* сохранить причину;
* учесть результат при оценке состояния подписки.

### FR-047. Превышение допустимого периода доставки

Если доставка не была успешно завершена в пределах установленного периода, сервис должен прекратить или изменить
дальнейшую обработку в соответствии с утверждённой политикой.

Результат должен быть зафиксирован.

### FR-048. Повторная доставка

Сервис должен допускать повторную отправку одного события одному получателю, если предыдущая попытка не получила
однозначного успешного подтверждения.

Каждая повторная попытка должна сохранять тот же идентификатор события.

---

## 9. Политики повторных попыток

### FR-049. Применение политики повторов

Для временных ошибок сервис должен применять утверждённую политику повторных попыток.

Политика должна определять как минимум:

* максимальное количество попыток;
* интервалы между попытками;
* максимальный период доставки;
* категории ошибок, для которых разрешён повтор;
* условия досрочного прекращения.

### FR-050. Изменение политики

Изменение политики повторов должно применяться только к новым доставкам.

---

## 10. Получение информации о доставках

### FR-051. Получение доставки по идентификатору

Клиент или сотрудник должен иметь возможность получить информацию о доставке по её идентификатору.

Регулирование доступа и уровней доступа вынесено из поля ответственности сервиса.

### FR-052. Получение доставок события

Сервис должен позволять получить список всех доставок конкретного события.

Для каждой доставки должны быть доступны:

* клиент;
* подписка;
* текущее состояние;
* количество попыток;
* итоговый результат;
* время последнего изменения.

### FR-053. Получение доставок подписки

Клиент должен иметь возможность получить список доставок по собственной подписке.

Должна поддерживаться фильтрация как минимум по:

* периоду;
* состоянию;
* типу события;
* результату;
* наличию ошибки.

### FR-054. Получение причины неуспешной доставки

Клиенту или сотруднику должна предоставляться понятная причина неуспешной доставки.

---

## 11. Бизнес-контроль

В рамках MVP аналитика и бизнес контроль отдельно не реализуется.

---

## 12. Уведомления о состоянии подписки

### FR-055. Уведомление об автоматическом отключении

После автоматического перевода клиента в состояние `disabled` клиент может узнать об этом, запросив информацию о себе.

Необходимость отдельного уведомления через дополнительный канал определяется отдельно.

### FR-056. Уведомление о неуспешном включении

Если endpoint не прошёл проверку при попытке включения подписки, клиент должен получить:

* результат проверки;
* понятную причину отказа;
* время проверки.

### FR-057. Уведомление об успешном включении

После успешного перевода подписки в состояние `active` клиент должен получить подтверждение возобновления.

---

## 13. Проверка endpoint

### FR-058. Запуск проверки endpoint

Проверка endpoint должна выполняться как минимум:

* при создании клиента;
* при редактировании клиента;
* при изменении endpoint;
* при включении клиента из `disabled`.

### FR-059. Результат проверки endpoint

Результат проверки должен содержать:

* успешность проверки;
* время выполнения;
* категорию ошибки;
* допустимое для клиента описание причины;
* проверенный endpoint.

### FR-060. Проверка версии контракта

Если проверка endpoint предусматривает подтверждение поддерживаемой версии контракта, сервис должен убедиться, что
получатель готов принимать выбранную версию.

Необходимость такого подтверждения определяется интеграционным контрактом.

### FR-061. Отсутствие доставки бизнес-событий при проверке

Проверка endpoint не должна приводить к отправке реального бизнес-события, если это явно не предусмотрено контрактом.

Для проверки должно использоваться отдельное тестовое сообщение или специальный запрос.

---

## 14. Версионирование событий

### FR-062. Поддержка версии события

Каждое принимаемое событие должно содержать версию формата или контракта.

### FR-063. Выбор версии клиентом

При регистрации клиент должен выбрать одну из доступных ему поддерживаемых версий.

### FR-064. Сохранение совместимости существующей подписки

В рамках одной версии контракта доступен только определённый набор событий.

### FR-065. Миграция клиента на новую версию

Клиент должен иметь возможность перевести все подписки на новую поддерживаемую версию по установленной процедуре.

Перед применением новой версии может потребоваться повторная проверка endpoint.

### FR-066. Прекращение поддержки версии

Если поддержка версии прекращается, сервис должен позволить:

* запретить создание новых подписок на эту версию;
* уведомить существующих клиентов;
* установить срок завершения поддержки;
* прекратить использование версии после утверждённой даты.

---

## 15. Обработка изменений подписки и событий

### FR-067. Проверка состояния подписки при создании доставки

Сервис должен учитывать состояние подписки в момент создания доставки.

Если подписка не находится в состоянии `active`, доставка не должна создаваться.

### FR-068. Проверка состояния клиента при создании доставки

Сервис должен учитывать состояние клиента в момент создания доставки.

Если клиент не находится в состоянии `active`, доставка не должна создаваться.

### FR-069. Изменение подписки во время обработки

При отключении клиента сервис должен прекратить дальнейшую обработку всех ожидающих доставок этого клиента.

Конкретный способ прекращения обработки определяется архитектурой сервиса.

### FR-070. Изменение endpoint при ожидающих доставках

Изменение endpoint клиента применяется только к новым доставкам.

Для уже созданных доставок используется endpoint, зафиксированный в момент их создания.

### FR-071. Изменение версии контракта при ожидающих доставках

Изменение версии контракта подписки не должно менять версию уже созданных доставок, если отдельным решением не
определено иное.
